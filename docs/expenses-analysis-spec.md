# XpenseDesk — Expenses Analysis UX/UI Specification

Route: `/manager/history`
This document is a platform-agnostic UX/UI spec for the Expenses Analysis screen. It describes layout, behavior, and visual design without framework-specific language.

## 1. Purpose

The Expenses Analysis screen allows managers to explore spending patterns across billing cycles, employees, and categories. It follows a **master–detail** layout:

- **Master** (top): 12-month bar chart or table of total approved spend per cycle.
- **Detail** (bottom): Drill-down analysis for the selected cycle — switchable between category bars, employee bars, and a pivot table.

Data is fetched from the backend in two explicit steps:

1. **Run report** loads the master grid for the selected filters.
2. After the master grid is loaded, the app selects the active cycle and runs the detail report for that cycle.

Filters must be explicitly executed via a **Run** button before results update.

---

## 1.1 Implementation Constraints

- Before building the analysis feature itself, refactor out and reuse the shared report-table infrastructure already proven in the Expenses Report screen.
- Use the same report widget foundation used by the Expenses Report, centered on the existing `DesktopExpenseTable` / `SectionTable` table infrastructure, rather than introducing a second scrolling table implementation.
- This is preliminary infrastructure work and must be validated first so we do not reintroduce horizontal/vertical scrolling bugs that were already solved in the Expenses Report.
- Step 0 is not optional: verify that the Expenses Report still behaves correctly after the shared widget/table refactor before continuing with Expenses Analysis feature work.
- The filter pane must reuse the existing Flutter selector widgets instead of introducing new filter controls.
- Desktop uses the existing `EmployeeSelector` and `CategorySelector` widgets directly.
- Mobile can wrap the same selector logic in a dialog or sheet container, but must preserve the same summary text, selection rules, and select-all / clear behavior.
- Excel export is generated in the Flutter client from already-loaded report data. The backend does not provide Excel files for this screen.
- Detail interactions must support drill-through into the Expenses Report screen with embedded query parameters.

## 4. Filters Card

### 4.1 Desktop Layout

A horizontal row with three elements:

| Element | Description |
|---|---|
| **Employee selector** | Reuse the existing `EmployeeSelector` widget. Multi-select popover. Shows "All employees" when all selected, count otherwise (e.g., "3 selected"). Includes `Select All` / `Clear` actions at the top. |
| **Category selector** | Reuse the existing `CategorySelector` widget. Same pattern as employee and uses category aliases as the filter values. |
| **Run button** | Primary filled button with a play (▶) icon and "Run" label. **Disabled** when filters haven't changed since last run. Enabled as soon as any checkbox is toggled. |

The spec should stay aligned with the current selector components rather than defining a separate bespoke filter UI. Visual refinements can be applied around those widgets, but the selection contract and summary behavior should remain shared.

### 4.2 Pending vs Applied State

- Toggling a filter checkbox marks filters as **dirty** (Run button becomes enabled).
- Charts and tables always reflect the **last applied** filter state.
- Pressing Run copies pending filters into applied state and calls the **master report API**.
- The master report response replaces the full 12-cycle dataset shown in the Monthly Breakdown card.
- After the master report completes, the app selects the active cycle from the returned dataset and immediately calls the **detail report API** for that cycle.

### 4.3 Mobile Layout

- Filters are hidden behind a header icon button (sliders icon).
- Active filter count shown as a badge on the icon.
- Tapping opens a centered modal/dialog with both dropdowns stacked vertically.
- Modal has a "Clear All" reset action and a full-width "Run" button at the bottom.
- The mobile container may differ, but it still uses the same employee/category selection components and selection rules as desktop.

## 5. Master Card — Monthly Breakdown

### 5.1 Header

- **Title**: Trend icon + "Monthly Breakdown" in muted text.
- **Config widget** (right-aligned): A bordered, rounded container with:
  - **Toggle group** (single select): Bar chart icon | Table icon.
  - Vertical separator.
  - **Export button**: Outline style, "Export" label with download icon. Exports all 12 months as an Excel file.

### 5.2 Data Range

- **12 months ending with the active cycle.** For active cycle `03/2026`, the range is `04/2025` through `03/2026`.
- Each cycle row comes from the master report API and includes raw fields for `date`, `cycleId`, `cycleLabel`, and `totalApproved`.
- The app maps those raw rows into UI objects that also expose `from` date, `to` date, `month`, `year`, and `isActive` for rendering.
- The **active cycle** is always the **last bar** in the chart.

### 5.3 Master Report API Contract

The **Run** CTA calls the master report endpoint with the applied employee/category filters.

Expected raw row shape:

| Field | Type | Notes |
|---|---|---|
| `date` | date/string | Source period value returned by the API for the cycle row. |
| `cycleId` | string | Stable identifier used by the detail report and drill-through links. |
| `cycleLabel` | string | Display label such as `03/2026`. |
| `totalApproved` | number | Total approved spend for the cycle under the applied filters. |

Client object created from that data:

| Object | Purpose |
|---|---|
| `ExpensesAnalysisMasterRow` | Raw DTO mirroring the API contract. |
| `AnalysisCycleSummary` | UI-facing model used by the master chart/table. Contains `cycleId`, `cycleLabel`, `totalApproved`, derived period metadata, and `isActive`. |

### 5.4 Bar Chart View (default)

- Vertical bar chart, 12 bars, one per cycle.
- X-axis: cycle labels (e.g., "04/2025", "05/2025", …).
- Y-axis: dollar amounts.
- Grid: dashed lines, muted color.
- Each bar has rounded top corners (4px radius).
- **Bar colors**:
  - **Selected cycle**: Full primary color (100% opacity).
  - **All other bars**: Primary at 25% opacity.
  - The active cycle does NOT get special bar coloring — it looks the same as any unselected bar.
- **Value labels**: Formatted currency shown above each bar (10sp, foreground color).
- **Active cycle indicator**: Below the X-axis label of the active (last) bar, render a small **pill badge**:
  - Rounded rectangle (36×14px, full-radius corners).
  - Primary background color, white text.
  - Text: "Active" (8sp, bold).
  - Positioned just below the date label.
- **Click interaction**: Clicking any bar selects that cycle and updates the Detail card below.
- **Hint text**: Centered muted text below the chart: "Click a month to analyze".

### 5.5 Table View

- Two columns: Cycle label (left) | Total Approved (right, formatted currency).
- Table header row has `muted/50` background.
- **Selected row**: Highlighted with `primary/5` background + bold text.
- **Active cycle row**: Shows an "Active" badge next to the label.
- Rows are clickable — same behavior as clicking a bar.

### 5.6 Export

- File name: `monthly-breakdown-YYYY-MM-DD.xlsx`
- Columns: Cycle, Period (from – to), Total Approved.
- Export is generated in Flutter from the currently loaded master dataset. No backend export endpoint is used.

## 6. Detail Card — Cycle Analysis

### 6.1 Header

- **Title**: The selected cycle label (e.g., "03/2026").
  - If the selected cycle is the active cycle, an "Active" badge appears inline (primary background, 10sp text).
- **Subtitle**: Date range (e.g., "03/01/2026 – 03/31/2026") in muted, small text.
- **Config widget** (right-aligned): Same bordered container pattern as Master.
  - **Toggle group** (single select, 3 options):
    1. Bar chart icon + "By Category" label.
    2. People icon + "By Employee" label.
    3. Table icon (no label).
  - Vertical separator.
  - **Export button**: Same as Master. Exports pivot data as Excel.

### 6.2 Empty State

If no data exists for the applied filters: centered muted text "No approved expenses".

### 6.3 Detail Report API Contract

Once the master data is loaded, the app picks the active cycle and runs a second API for the selected cycle.

Expected raw detail row shape:

| Field | Type | Notes |
|---|---|---|
| `employeeId` | string | Stable user identifier. |
| `employeeName` | string | Display name used in charts and table rows. |
| `categoryAlias` | string | Category key used for labels, coloring, and drill-through filters. |
| `amount` | number | Approved amount for the employee/category tuple. |

Client objects created from that data:

| Object | Purpose |
|---|---|
| `ExpensesAnalysisDetailRow` | Raw DTO mirroring the API contract. |
| `CategoryBreakdownItem` | Aggregated total by category for the category chart. |
| `EmployeeBreakdownItem` | Aggregated total by employee for the employee chart. |
| `EmployeeCategoryPivotRow` | One employee row in the pivot table with category totals and row total. |
| `ExpensesAnalysisDetailState` | Consolidated UI model containing the three detail views for the selected cycle. |

### 6.4 View: By Category (default)

- Vertical bar chart showing total spend per expense category.
- X-axis: Category labels (localized).
- Each bar has a **unique color** matching the category color palette (§4.5).
- Value labels above each bar (formatted currency).
- Chart height: 350px.
- Clicking a category bar drills into the Expenses Report screen for the selected cycle and category.

### 6.5 View: By Employee

- Vertical bar chart showing total spend per employee.
- X-axis: Employee names (11sp, no rotation, show all labels).
- Each bar has a **unique color** matching the employee color palette (§4.4).
- Value labels above each bar.
- Bars sorted descending by total.
- Chart height: 350px, extra bottom margin (40px) for name labels.
- Clicking an employee bar drills into the Expenses Report screen for the selected cycle and employee.

### 6.6 View: Pivot Table

A matrix table: rows = employees, columns = categories + total.

| Structure | Details |
|---|---|
| **Header row** | "By Employee" column + one column per active category (right-aligned) + "Total Approved" column (right-aligned, bold). Background: `muted/50`. |
| **Data rows** | Employee name (primary color, bold) + category amounts (right-aligned, formatted currency) + row total (right-aligned, bold). |
| **Grand total row** | "Total Approved" label + column totals + grand total. Background: `muted/30`, bold text. |
| **Sorting** | Rows sorted descending by employee total. |
| **Scrolling** | Horizontal scroll if columns overflow container width. |

Interaction rules:

- Clicking an employee name drills through with `cycleId` + `employees`.
- Clicking a category column label drills through with `cycleId` + `categories`.
- If a specific employee/category cell becomes clickable, it should pass both filters.

### 6.7 Export

- File name: `pivot-{cycleId}-YYYY-MM-DD.xlsx`
- Sheet name: "Pivot".
- Columns: Employee + one column per active category (localized names) + Total.
- Last row: Grand totals.
- Export is generated in Flutter from the loaded detail-state object. No backend export endpoint is used.

## 8. Interaction Flow

1. Page loads → Filters default to "All employees" + "All categories".
2. Initial load behaves like an automatic first Run so the screen is populated without requiring user interaction.
3. User toggles filter checkboxes → Run button activates, but currently rendered data does not change yet.
4. User clicks **Run** → Applied filters update → master report API returns the cycle summary grid.
5. The app maps the master rows into cycle-summary objects, marks the returned active cycle, and renders the Monthly Breakdown card.
6. The app immediately calls the detail report API for the active cycle and builds the category chart, employee chart, and pivot-table objects from the returned rows.
7. User clicks a bar (or table row) in Master → Detail report API re-runs for that selected cycle.
8. User switches Detail view mode via toggle → Content swaps (category bars / employee bars / pivot table).
9. User clicks a category or employee in the Detail card → navigate to the Expenses Report route with embedded query parameters.
10. User clicks Export → Flutter generates and downloads the Excel file.

### 8.1 Drill-through Navigation Contract

- Target route: `/manager/history/report`
- Required query parameter: `cycleId={selectedCycleId}`
- Optional employee filter: `employees={employeeId}`
- Optional category filter: `categories={categoryAlias}`
- If the interaction identifies both dimensions, pass both `employees` and `categories`.
- The destination screen should open already filtered from the embedded query string.
